# 领域建模与代码库设计参考

来源：`https://github.com/mattpocock/skills`（MIT）。DW 只吸收其中的 `domain-modeling` 纪律并参考 `codebase-design` 的架构判断；不安装上游插件、Skill、脚本或配置，也不允许隐式调用。

## 触发边界

- `domain-modeling`：仅在用户明确要求建立或修改领域术语、统一语言、术语表或 ADR 时使用。普通开发、仅阅读既有领域文档或模型自行发现术语歧义，不触发本流程。
- `codebase-design`：仅在用户明确要求架构设计、模块接口设计、重构边界或可测试性分析时作为参考。项目现有术语、架构规范和用户表述优先，不强制采用上游词汇。
- 两者均由当前模型负责判断和执行，不新增计划、审查、测试或任务状态负责人。

## 术语表纪律

1. 先读取项目既有术语表、领域文档和相关代码，不创建平行词汇表。
2. 区分领域概念与实现细节；术语表只记录业务含义、边界和关系，不充当规格说明或实现笔记。
3. 对模糊、重载或相互冲突的词，使用具体场景和边界案例澄清，并核对代码是否与陈述一致。
4. 术语形成稳定共识后，写入项目指定的术语表位置；没有既定位置时先与用户确认，不自动规定 `CONTEXT.md`。

## ADR 判定

仅当以下三项同时成立时才建议或创建 ADR：

1. 难以撤销：未来改变决定具有显著成本。
2. 原因不明显：缺少背景时，后续维护者会合理地追问为什么这样选择。
3. 存在真实权衡：评估过可行替代方案，并基于明确代价作出选择。

任一条件不成立就不创建 ADR。写入前遵循项目已有 ADR 目录、编号和模板；项目没有约定时先确认存放方式。

## 代码库设计参考

- 评估接口是否以较小认知表面承载足够行为，并把复杂性集中在实现内部。
- 优先让变化、故障知识和验证集中在一个位置，避免把同一规则散落到调用方。
- 让调用方和测试使用同一公开接口；依赖应可替换，结果应尽量可观察。
- 只有存在真实变化点或第二种实现时才引入抽象边界，避免为假设中的扩展建立层次。
- 可使用“删除后复杂性会消失还是扩散到调用方”检验抽象是否真正承担职责。

这些是分析问题的参考问题，不是强制命名规范。最终设计必须结合仓库现状、行为需求、测试证据和迁移成本。
