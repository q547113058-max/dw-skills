## 设计分流

先判断当前界面属于哪一类，再选择审美策略。

### 品牌型界面

适用于：

- 落地页、营销页、活动页、作品集、品牌官网、长文内容页、关于页。
- 用户第一印象本身就是交付物。

规则：

- 设计必须有明确观点，不能只追求“干净”和“现代”。
- 允许更强的视觉记忆点：图像、排版、色彩、动效、节奏和叙事结构。
- 不要把所有品牌页都做成同一种编辑杂志风、紫蓝科技风或三卡片 SaaS 风。
- 如果内容暗示实物、地点、人物、产品或场景，必须使用真实图片、生成图片、截图或可信视觉资产。
- 品牌型页面优先使用 `taste-skill` 判断审美方向，再用 `frontend-design` 固化 tokens 和 QA。

### 产品型界面

适用于：

- App UI、后台、仪表盘、设置页、表单、工具、数据表、认证后工作台。
- 用户目标是完成任务，设计服务于效率和信任。

规则：

- 熟悉、稳定和一致优先于惊艳。
- 使用标准导航、表单、表格、弹窗、菜单、标签页和状态反馈，不为了风格重造基础控件。
- 保持统一组件词汇：同类按钮、输入框、状态、图标和间距在不同页面中一致。
- 动效只表达状态、反馈、加载或转场，不做装饰性表演。
- 产品型界面优先保证可用性、可访问性、状态完整性和响应式结构。

## 设计上下文文件

当项目有持续 UI 工作时，使用以下文件沉淀设计上下文：

- `docs/project-product-context.md`：产品类型、目标用户、主要任务、使用环境、核心流程、约束。
- `docs/project-design-spec.md`：设计方向、品牌语气、参考与反参考、颜色、字体、间距、圆角、组件规则、动效规则。

规则：

- 新项目或大改版前，先写最小可用版本，不需要一次写完整设计系统。
- 已有设计 token、组件库或品牌资产时，以现有系统为准，不凭个人审美覆盖。
- 设计选择变化时同步更新 `docs/project-design-spec.md`，不要只留在聊天记录中。

## 体验原则

- 为目标用户和真实工作流设计。
- 第一个屏幕直接展示可用体验，不默认做营销式落地页。
- 信息层级要清楚：主操作、次操作、状态和反馈必须容易区分。
- 常用流程要高效，重复操作要省力。
- 每个交互状态都要考虑：默认、hover、focus、active、disabled、loading、empty、error、success。

## 审美反模式

以下模式默认避免，除非用户需求、品牌资产或现有产品明确要求：

- 默认紫蓝渐变、暗色网格、发光球、玻璃拟态和泛 AI 科技感。
- 所有区块都使用相同的三列卡片、图标在上文字在下。
- 卡片套卡片、宽阴影加细边框的“幽灵卡片”、无意义大圆角。
- 每个 section 都有小号大写 eyebrow、编号 eyebrow 或装饰性状态点。
- 品牌页没有真实视觉资产，只靠渐变、文本和假截图撑场面。
- 产品 UI 为了“有设计感”使用奇怪控件、过度动效或不符合平台习惯的交互。
- 灰色文字直接放在彩色背景上，导致低对比和发灰。
- 纯黑、纯白、默认米色/沙色、深蓝/石板色或棕橙咖啡色作为无理由主视觉。
- 假精确数据、模板化公司名、无来源评价、占位头像和无意义版本号。

反模式不是绝对禁用项。允许使用时必须能说清：

- 它服务什么用户目标或品牌语气。
- 它是否来自现有品牌或真实数据。
- 它如何通过对比度、响应式、状态和性能检查。

## 布局

- 页面区域使用全宽区块或不加框的约束布局。
- 不把卡片套在卡片里。
- 卡片只用于重复项、模态框或确实需要框住的工具。
- 固定格式元素使用稳定尺寸：棋盘、网格、工具栏、图标按钮、计数器、列表项等不能因 hover、标签或加载文字导致布局跳动。
- 文本不能重叠、裁切或溢出容器。
- 移动端和桌面端都要检查可读性。

## 控件

- 工具按钮优先使用图标，存在合适图标时使用 lucide 或项目已有图标库。
- 颜色选择使用 swatches。
- 模式选择使用 segmented controls。
- 二元设置使用 checkbox 或 toggle。
- 数值设置使用 slider、stepper 或输入框。
- 选项集合使用 menu 或 tabs。
- 命令按钮使用清晰文本或图标+文本。

## 颜色

- 使用有意图的调色板：一个主色、支持中性色和明确状态色。
- 避免单一色相的界面。
- 避免默认紫蓝渐变、米色/沙色、深蓝/石板色、棕橙咖啡色成为无理由主视觉。
- 状态色要语义清楚：成功、警告、错误、信息。
- 新项目优先使用语义化颜色 token，而不是在组件里散落硬编码颜色。
- 同一页面的主强调色要一致；不要在不同区块随意切换 CTA 颜色。
- 文本对比度必须可读：正文至少满足 WCAG AA，弱文本和 placeholder 也不能低到不可读。

## 字体和文案

- 文案简洁。
- 标题大小匹配容器；不要在紧凑面板里使用 hero 级字体。
- 不用视口宽度缩放字体。
- 字距保持 `0`，不使用负字距。
- 按钮、卡片、面板内文字必须适配最长词。
- 品牌型界面先定义语气词和参考对象，再选择字体；不要把“高级”“创意”自动翻译成衬线字体。
- 产品型界面通常使用单一清晰字体族即可，避免在标签、按钮和数据中使用展示字体。
- 长正文控制行长，默认不超过 `65-75ch`。
- 交付前通读可见文案，删除 AI 腔、空泛动词、断裂比喻和无意义微文案。

## 动效

- 动效必须服务层级、叙事、反馈或状态变化。
- 产品型界面常规转场控制在 `150-250ms`，避免让用户等待表演。
- 品牌型界面可以使用更强动效，但必须有 reduced motion 降级。
- 不动画布局属性，优先使用 `transform` 和 `opacity`。
- 不用滚动监听频繁写 React state；使用框架已有 motion API、IntersectionObserver 或成熟动画库。

## 设计审查配方

UI 交付前按以下顺序做设计审查：

1. **Design read**：确认界面属于品牌型还是产品型，目标用户、场景和风格判断是否明确。
2. **Design system discovery**：查找已有 token、组件、样式、品牌资产和相邻页面，不重复造轮子。
3. **Layout review**：检查层级、对齐、间距、响应式、横向溢出、文本重叠和固定尺寸元素跳动。
4. **Typography review**：检查字体选择、标题层级、行长、行高、按钮换行和文案语气。
5. **Color review**：检查主色一致性、状态色语义、对比度、暗色/亮色模式和硬编码颜色。
6. **Interaction review**：检查 hover、focus、active、disabled、loading、empty、error、success。
7. **Anti-template review**：检查是否落入默认三卡片、重复 eyebrow、假截图、紫蓝渐变、玻璃拟态等模板痕迹。
8. **Evidence review**：可行时用浏览器、截图或自动检测证明桌面和移动端可用；不能验证时记录原因。

## UI 验收

交付前检查：

- [ ] 视觉方向符合需求。
- [ ] 已判断品牌型或产品型界面，并采用对应审美策略。
- [ ] 关键设计上下文已记录到 `docs/project-product-context.md` 或 `docs/project-design-spec.md`（适用于持续 UI 项目）。
- [ ] 主色、字体和间距已记录。
- [ ] 主要流程可完成。
- [ ] 桌面和移动端无重叠、裁切或横向溢出。
- [ ] 可点击元素有清晰状态。
- [ ] 空、加载、错误和成功状态已处理。
- [ ] UI 不像默认模板或未打磨组件库。
- [ ] 已完成反模板化审查，默认 AI 感模式有明确规避或理由。
